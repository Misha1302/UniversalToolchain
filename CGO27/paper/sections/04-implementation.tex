\section{Implementation}
We implement the model in System W, an extensible .NET compiler. The contract owner is a production module shared by selection, compilation observers, and experiment runners. A fact state exposes \texttt{valid}, \texttt{invalid}, and \texttt{unknown}; an effect contract contains normalized \texttt{requires}, \texttt{produces}, \texttt{preserves}, and \texttt{invalidates} sets; and each \texttt{VerificationObligation} stores fact, rule, canonical owner, creation boundary, and first eligible boundary.

Pipeline observers receive actual bytecode, AIR, and optimized AIR artifacts. Effect validation follows selected module occurrence order rather than sorting by module name. It rejects missing requirements, invalid preservation claims, repeated ambiguous occurrences, and invalidations without a canonical verifier route. The scheduler uses deterministic rule/fact ordering and rejects unknown policies, unknown demand queries, route conflicts, owner mismatches, and missed deadlines.

The production verifier registry currently exposes canonical bytecode, AIR, and backend-input owners. The studied integration chooses an immediate deadline for each observed invalidation because the owning verifier is executable at the same boundary. This is a conservative implementation of the general model: it does not claim deferred multi-boundary obligation persistence.

P0, P1, P1D, P2, and P3 share the same structural and semantic verifier implementations. P1D adds only an execution-scoped demand set; it does not alter the artifact or oracle. P2 schedules due obligation routes. P3 schedules all routes applicable at the boundary. Telemetry records policy, fact invalidations, obligations, demand queries, verifier invocations, first detection boundary, diagnostics, elapsed verifier time, allocations, and process identity.

\subsection{Admissibility and boundary procedure}
Contract admission is separated from policy execution. Selection first normalizes fact identifiers, effect sets, route identifiers, and owner identities. It then resolves every selected fact to at most one canonical verifier owner and rejects duplicate owners, a verifier whose required artifact is unavailable at the declared boundary, or an invalidation with no executable route. This preflight prevents a later policy choice from changing which checker is authoritative. It also keeps P1D, P2, and P3 comparable: they differ in scheduling, not in verifier implementation or route resolution.

At each observed boundary the scheduler takes an immutable snapshot of the selected contract state and performs four ordered steps. First, it validates all requirements and preservation claims against the incoming fact state. Second, it applies produced and invalidated effects in selected occurrence order; each invalidation creates an obligation whose lineage records the triggering component and boundary. Third, it computes the execution set: P1D chooses only invalidated facts named by explicit demand queries, P2 chooses obligations whose first eligible boundary is current, and P3 chooses every applicable canonical route. Fourth, it executes routes in deterministic rule/fact order. A successful verifier marks its fact valid and discharges all matching due obligations; rejection, an unknown result, an owner mismatch, an unresolved route, or an overdue obligation stops compilation.

The implementation deliberately does not infer a route from a nearby component name or from registration order. Such inference would make correctness depend on composition accidents that are invisible to the effect contract. Repeated occurrences are accepted only when their normalized effects and ownership are unambiguous. This is why occurrence order, owner identity, missing-route handling, and conflict rejection appear both as production invariants and as separate ablation mechanisms.

The same procedure feeds the experiment telemetry. Every record includes the pre-effect state, normalized effect, created obligation, selected execution set, route result, and post-boundary state. The analyzer can therefore distinguish ``no obligation was created,'' ``an obligation was deferred,'' ``a route rejected,'' and ``the backend later failed.'' That distinction is essential for the matched P1D counterexample and for checking the theorem against actual scheduler behavior rather than only final program output.

\paragraph{System W language path.}
The source-to-result runner executes the normal dialect engine, optimizer, production verifier, and CIL/interpreter backends in fresh processes. Research policy switches remain internal/friend APIs and do not expand the shipped facade. P3 remains the normal strongest checking profile.

\paragraph{Language T public-SDK path.}
A separate small language package uses only the public extension SDK. Its shape/layout facts and verifier route differ from System W's arithmetic/capability relations, while the scheduler and contract representations are shared. We do not call the package independently authored: its cases were created during this study.

\paragraph{Baseline defect repair.}
Historical source-to-result case P07 mixed double parameters with an integer literal and failed under every policy before a result. We retained the historical receipt, repaired the independent numeric-dispatch defect with an explicit finite promotion matrix, added CIL/interpreter regression coverage, versioned the corpus, and reran the unchanged source and oracle. P07 now produces 13 under every policy and is counted as a valid control only in the new protocol.

The exact pre-hardening master contract was 1,597 passing tests. New test counts are reported only after mechanical discovery on the final branch head; the historical count is not rewritten.
