        # Commit 02 — Introduce an explicit CIL intrinsic registry

## High-level idea

Create a single explicit CIL-backend registry that owns intrinsic compile semantics and the supported-intrinsic list.

This commit does **not** yet replace AIR type simulation.  
Its job is to remove the first major duplication:

- compile handlers,
- supported intrinsic names.

After this commit, the CIL backend compile path should stop hardcoding intrinsic knowledge in multiple unrelated places.

## Why this is a separate commit

If you jump straight into type simulation refactoring, it becomes harder to isolate mistakes.  
This commit establishes the new center of truth for compile-time intrinsic behavior first.

That gives you:

- a clean object model,
- stable lookup semantics,
- one place to grow future intrinsic families,
- a safer base for the next commit.

## Non-goals

- Do not migrate `AbstractMethodsCompilerImpl.GetReturnType(...)` yet.
- Do not remove `AirTypes` yet.
- Do not change optimizer behavior yet.
- Do not try to solve all architectural issues in one patch.

## Core design target

Introduce a backend-specific immutable descriptor model, for example:

```csharp
internal sealed record CilIntrinsicDescriptor(
    string Name,
    Action<CompilationContext, Instruction, List<Type>> Compile,
    Action<Instruction, List<Type>> ProcessTypes);
```

and a registry like:

```csharp
internal sealed class CilIntrinsicRegistry
{
    public IReadOnlyList<string> SupportedIntrinsics { get; }
    public bool TryGet(string name, out CilIntrinsicDescriptor descriptor);
    public CilIntrinsicDescriptor GetRequired(string name);
}
```

The exact names can differ, but the architecture should preserve these ideas:

- descriptors are explicit,
- lookup is deterministic,
- the registry is immutable after construction,
- supported names come from descriptors, not from an unrelated duplicated list.

## Files likely to change

Main files:

- `UniversalToolchain/BytecodeDynamicMethodsCompiler/Compilers/AbstractMethodsIntrinsicCompiler.cs`
- new files under the same project, likely:
  - `CilIntrinsicDescriptor.cs`
  - `CilIntrinsicRegistry.cs`

Possibly supporting helpers if you want cleaner decomposition:
- `CilIntrinsicDescriptorBuilder.cs`
- `CilIntrinsicFamilies.cs`

## Detailed implementation instructions

### 1. Introduce a descriptor type

Create a small internal type for one CIL intrinsic.

Recommended shape:

- `Name`
- `Compile`
- `ProcessTypes`

Even though `ProcessTypes` will not be fully used until the next commits, define it now so the registry shape is already correct.

Why define both now:
- it prevents another redesign in the next commit,
- it makes the real target model explicit,
- it avoids introducing another temporary abstraction later.

### 2. Introduce a registry class

Create an internal immutable registry that builds and stores all descriptors.

Key requirements:
- keys are intrinsic names,
- ordering is deterministic,
- duplicate names fail fast,
- `SupportedIntrinsics` is derived from registered descriptors,
- lookup is O(1) via a dictionary.

Recommended behavior:
- constructor populates descriptors,
- after construction the internal dictionary is not mutated.

### 3. Move compile handlers into the registry

Take the existing compile handlers from `AbstractMethodsIntrinsicCompiler` and relocate their registration into the new registry.

This includes:
- `call C#`
- `call C# ctor`
- `store_local`
- `load_local`
- `load_local_ref`
- `load_external`
- `store_external`
- `load_bool`
- `boolean_and`
- `boolean_or`
- `boolean_not`
- `load_i32`
- `load_i64`
- `load_f32`
- `load_f64`
- `load_decimal`

Also handle the arithmetic and comparison families in a registry-backed way rather than through a disconnected `SupportedIntrinsics` list.

You may implement family registration with helper methods such as:

```csharp
private static void RegisterArithmeticFamily(...)
private static void RegisterComparisonFamily(...)
```

### 4. Refactor `AbstractMethodsIntrinsicCompiler` to become a thin executor

After the registry exists, `AbstractMethodsIntrinsicCompiler` should stop owning the compile mapping directly.

Instead:
- it receives or creates the registry,
- looks up the descriptor by name,
- executes `descriptor.Compile(...)`.

Recommended direction:
- keep the public surface of `AbstractMethodsIntrinsicCompiler` stable for now,
- reduce its responsibilities to orchestration rather than ownership of intrinsic metadata.

### 5. Derive `SupportedIntrinsics` from the registry

This is critical.

Do **not** maintain:
- a hand-written `SupportedIntrinsics` property,
- plus a separate actual handler map.

`SupportedIntrinsics` must come from registry descriptors.

That is one of the main reasons for this commit.

### 6. Keep helper methods localized and reusable

Existing helper methods such as:
- arithmetic emitters,
- comparison emitters,
- type parsing helpers,
- cast helpers,
- stack pop/push helpers,

can remain in `AbstractMethodsIntrinsicCompiler` **or** move into private static helpers used by the registry builder.

The key rule:
- helper location is flexible,
- ownership of intrinsic registration is not.

## Quality constraints

- Do not introduce reflection-based or service-locator style lookup for intrinsic descriptors.
- Do not expose the registry as public framework API unless truly needed.
- Keep it internal to the CIL compiler project unless you later prove broader reuse.

## Suggested validation

### Behavioral checks
- All current CIL compile tests should still pass except the ones still blocked by old type simulation.
- `SupportedIntrinsics` must still contain every intrinsic the backend can compile.

### Structural checks
Add a small internal test if useful:
- every descriptor name in the registry is unique,
- `SupportedIntrinsics` equals the sorted/declared registry key set.

You may postpone dedicated tests to commit 06, but if adding them here is easy, do it.

## Acceptance criteria

This commit is complete when:

- CIL compile semantics are registered through one explicit registry,
- `SupportedIntrinsics` is derived from that registry,
- `AbstractMethodsIntrinsicCompiler` no longer duplicates intrinsic names in a separate hand-maintained list,
- build still passes.
