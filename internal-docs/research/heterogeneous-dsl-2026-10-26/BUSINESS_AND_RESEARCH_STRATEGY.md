# UTS: ценность, научный вклад и выбор ближайшего направления

**Статус: dated-review и proposal, 2026-10-26.** Основание — исходники и исследования на `4baf8847cb91eda323395c9a8cce0b20bd88ffcd`, первичные публикации и документация альтернатив. Здесь разделены наблюдения, предлагаемые решения и непроверенные гипотезы. Это не новый runtime contract, отчёт о продажах, подтверждение научной новизны или выполненный CPU/GPU benchmark. Текущую архитектурную authority сохраняет [CURRENT_ARCHITECTURE_STATUS](../../../docs/CURRENT_ARCHITECTURE_STATUS.md).

**Новое обязательное условие:** пользователь поставил цель журнальных Q1/Q2 публикаций, засчитываемых программой ВШЭ. [Публикационные требования и источники](PUBLICATION_REQUIREMENTS.md) фиксируют неизвестные правила, состояние journal shortlist и актуальность сроков. `CGO27` ниже обозначает существующий исследовательский корпус; он не подтверждает подачу, принятие или зачёт. [Независимый следующий анализ](NEXT_ANALYSIS_PROMPT.md) вправе пересмотреть приоритеты этого обзора с учётом нового условия.

## 1. Рекомендация

**Сохранить универсальную архитектуру UT, сузить ближайшее обещание и проверять ценность на внешних задачах.** Рабочая формулировка направления: framework для создания и сопровождения предметных языков с явной композицией, проверяемыми контрактами расширений и воспроизводимыми путями исполнения.

Ближайшие приоритеты различаются:

1. **Научный результат:** усилить уже существующее исследование повторной проверки контрактов в `CGO27/`. Основные пробелы — независимые ошибки, полнота declarations, сильный baseline и полное время компиляции. Новый GPU backend для этого не нужен.
2. **Практическая и коммерческая гипотеза:** один внешний пилот, которому нужны управляемые формулы/правила в .NET либо проверка взаимодействия расширений. Выбрать одну из этих задач по доступному владельцу проблемы. Ближе к интеграции сегодня Wist; более специфичен для исследований UT — PlanFuzz.
3. **Аппаратное направление:** ограниченный numerical DSL поверх существующего compiler/runtime, если найдена конкретная нагрузка и сформулирован ожидаемый выигрыш. Сам по себе запуск одного кода на CPU и GPU уже не обосновывает отдельный продукт.

Это уточняет предыдущую рекомендацию из [README](README.md): numerical DSL остаётся хорошим инженерным экспериментом **при выборе аппаратной ветки**, но его приоритет над существующим исследованием и внешним продуктовым пилотом не подтверждён. [SPEC_RESEARCH_PLAN](SPEC_RESEARCH_PLAN.md) описывает подготовку ТЗ именно для этой условной ветки.

Не следует одновременно превращать UTS в платформу бизнес-правил, универсальный tensor compiler и коммерческую fuzzing-платформу. Общий core сохраняется; предметные пакеты остаются обычными расширениями. Большие новые абстракции получают приоритет после повторяющейся измеренной потребности.

## 2. Какая ценность уже есть, а какая ещё требует доказательства

| Вид ценности | Что подтверждено | Что остаётся неизвестным |
|---|---|---|
| Инженерная | Работающий .NET framework, Wist interpreter/CIL, immutable composition plan, контракты, диагностика, тесты и release gates | Стоимость использования и сопровождения чужой командой на её задаче |
| Научная | Реализованный механизм reverification, ограниченные сравнительные эксперименты, второй language package, ablations и подготовленная статья | Независимая эффективность, отличие от ближайшего prior art, полезная экономия на полной компиляции |
| Образовательная и профессиональная | Реальный материал по компиляторам, API, экспериментам и воспроизводимости | Это само по себе не измерение спроса или дохода |
| Коммерческая | Можно сформулировать проверяемые предложения для конкретных пользователей | В рассмотренных материалах нет подтверждённых покупателей, платных пилотов, unit economics или повторяемого канала привлечения |
| Аппаратная | Есть extension points для typed artifacts, transforms и backend executors | Нет реализованного numerical CPU/GPU route и измерений его полезности |

Источники состояния: [архитектура](../../../docs/CURRENT_ARCHITECTURE_STATUS.md), [ограничения](../../../docs/limitations.md), [Wist facade](../../../UniversalToolchain/UniversalToolchain.Wist/WistEngine.cs), [CGO27 ledger](../../../CGO27/CLAIM_EVIDENCE_LEDGER.md), [PlanFuzz status](../../proposals/planfuzz/implementation-status.md), [проверки предыдущей работы](VALIDATION.md).

Прошедшие тесты подтверждают конкретные проверенные свойства. Их число не доказывает общий semantic soundness, superiority над MLIR или спрос. Два исправления этой ветки найдены аудитом исходников; их нельзя приписывать discovery yield PlanFuzz.

## 3. Реализуема ли цель «один код на разных устройствах»

**Да, для определённой модели вычисления и поддерживаемого подмножества.** Нужно заранее выбрать уровень обещания:

| Уровень | Реалистичное требование |
|---|---|
| Исходный код | Одна программа DSL компилируется для перечисленных target configurations |
| Семантика | Для допустимых входов сохраняются наблюдаемые эффекты, ошибки и согласованный численный контракт |
| Функциональное исполнение | Есть рабочие runtime, memory ownership и completion semantics для каждого поддерживаемого target |
| Производительность | На выбранном семействе задач выполнены отдельные целевые требования для каждого устройства |
| Артефакт поставки | Один пакет может содержать несколько target artifacts или переносимое IR с последующей компиляцией; одинаковый native machine code не является требованием |

SYCL уже предоставляет общую модель для разных устройств и прямо отделяет её от автоматической идеальной performance portability. ILGPU предлагает CPU, CUDA и OpenCL accelerators для .NET; IREE предоставляет compiler/runtime с CPU/GPU deployment routes. Это подтверждает выполнимость класса задач, но также задаёт сильные baseline. Источники: [SYCL](https://www.khronos.org/sycl/), [ILGPU](https://ilgpu.net/docs/02-beginner/01-context-and-accelerators/), [IREE](https://iree.dev/).

### 3.1. Что делать с кодом, уже оптимизированным под GPU

Возможность зависит от того, что выражает исходная программа. Для `matmul → bias → activation` можно сохранить общую математическую задачу и выбирать разные layout, tiles, vectorization и способы исполнения. Разделение algorithm/schedule уже развито в [Halide](https://halide-lang.org/).

CUDA-подобный код с barriers и shared memory тоже иногда переводится на CPU: это демонстрирует [Polygeist GPU-to-CPU research](https://arxiv.org/abs/2207.00257). Однако сохранять корректность и получать подходящую CPU-структуру — отдельная задача. [AdaptiveCpp](https://adaptivecpp.github.io/AdaptiveCpp/compilation/) описывает затраты CPU-исполнения barrier-heavy kernels и необходимость compiler transformations. Поэтому утверждение «GPU-код на CPU принципиально невозможен» неверно; обещание одинаково высокой скорости для любого такого кода также не обосновано.

Полезный контракт UTS: общий алгоритм, явные target requirements, допустимые target-specific schedules и диагностируемый отказ, когда нужной реализации нет. Специализированный быстрый путь может сосуществовать с корректным переносимым вариантом. Нельзя молча выдавать software fallback за hardware GPU execution.

Матричные блоки GPU, Google TPU и другие NPU требуют отдельных соглашений о типах, памяти и runtime. Поддержка формата IR не подтверждает исполнение на конкретном ускорителе. Компиляция для CPU **или** GPU также не равна автоматическому распределению одной программы между ними: последнее добавляет partitioning, transfers, synchronization и cost model.

### 3.2. Как понимать глобальную оптимизацию

Нужно различать три масштаба:

- **Локальный:** упрощение выражений, constant folding, локальное устранение повторений.
- **Программный:** fusion, выбор layout между операциями, lifetime/reuse буферов, устранение материализации, учёт общих промежуточных результатов.
- **Аппаратный:** размещение частей графа, transfers, batch size, kernel launches и перекрытие вычислений.

Лучшая локальная замена может ухудшить программу: fusion способен убрать промежуточный буфер, но увеличить register pressure или повторное вычисление общего результата. Значит, legality и profitability должны быть раздельны. Семантический контракт ограничивает допустимые преобразования; cost model и измерения выбирают среди них.

Для ближайшего numerical опыта достаточно одной оптимизации, использующей структуру всей выбранной программы, с независимым oracle и matched baseline. Учитывать compilation/amortization, host overhead, transfers, synchronization и memory residency. Формулировка «оптимально на любом процессоре» не задаёт проверяемого требования; нужна матрица workload × device × numerical policy × residency и согласованные метрики. Подробный протокол уже находится в [EXPERIMENT_PLAN](EXPERIMENT_PLAN.md).

## 4. Где UTS может отличаться от существующих систем

| Система или линия | Что уже закрывает | Какой дополнительный результат должен показать UTS |
|---|---|---|
| MLIR | Dialects, interfaces, общие analyses/transforms, несколько уровней IR | Удобную композицию и сопровождение предметных .NET языков; измеренную пользу конкретных contracts и diagnostics |
| LLVM pass manager | Preservation, invalidation и зависимости анализов | Пользу маршрутизации разнородных verifier по выбранной конфигурации сверх аккуратной обычной интеграции |
| IREE / ILGPU / другие аппаратные стеки | Существенную часть compilation/runtime portability | Доменную семантику, интеграцию и оптимизацию, которые стоят меньше собственной обвязки пользователя |
| Expression/rule libraries | Встраивание выражений и правил в приложение | Полезность требуемой пользователю композиции языка и воспроизводимых маршрутов, а не просто вычисление строки |
| Property testing и compiler fuzzing | Генерацию, shrinking, semantic/differential checks | Выявление определённых ошибок комбинаций program/configuration/lifecycle с полезным replay и reduction |

Источники: [MLIR interfaces](https://mlir.llvm.org/docs/Interfaces/), [LLVM New Pass Manager](https://llvm.org/docs/NewPassManager.html), [IREE](https://iree.dev/), [ILGPU](https://ilgpu.net/docs/02-beginner/01-context-and-accelerators/), [NCalc](https://github.com/ncalc/ncalc), [RulesEngine](https://microsoft.github.io/RulesEngine/), [FsCheck](https://fscheck.github.io/FsCheck/).

Совместимость с .NET и иной API — инженерное позиционирование, но не автоматическая научная новизна. Внешний semantic provider, помогающий старому consumer через известный interface, тоже требует сравнения с уже существующими интерфейсными механизмами. UT может быть полезным верхним слоем над MLIR/IREE; для такого выбора не требуется обещать их замену.

## 5. Бизнес: кто получает результат и за что может платить

Все сегменты и модели дохода ниже — **гипотезы для проверки**, а не найденные покупатели или оценка рынка.

### 5.1. Ближайшая к текущему коду гипотеза: предметные формулы в .NET

Предполагаемый пользователь — разработчик или platform engineer приложения, где правила/формулы часто меняются и должны иметь определённое поведение. Предполагаемый покупатель — руководитель, отвечающий за стоимость изменений, ошибок и сопровождения. Автор формул может быть разработчиком или предметным специалистом; это нужно выяснить до проектирования редактора.

Возможный полезный результат: формулу можно проверить на примерах, связать с выбранным набором разрешённых операций, воспроизвести её исполнение и диагностировать ошибку. Если пользователю нужны согласование, хранение версий, активация и rollback, это отдельный host workflow вокруг библиотеки. В текущем Wist он целиком не поставляется. Источники: [production integration](../../../docs/start/production-integration.md), [lifecycle](../../../docs/reference/lifecycle-concurrency-privacy.md).

Сильный substitute выбирается по реальной задаче: обычный C# с конфигурацией, NCalc, Dynamic Expresso, RulesEngine либо подходящий policy engine. [NCalc](https://github.com/ncalc/ncalc) уже имеет parameters, custom functions и lambda compilation; [Dynamic Expresso](https://github.com/dynamicexpresso/DynamicExpresso) предоставляет reusable delegates; [RulesEngine](https://microsoft.github.io/RulesEngine/) — JSON workflows и actions. `Compile<TDelegate>` само по себе недостаточно для отличия.

Первый пилот должен проверить одну полезную особенность UTS сверх такого baseline: например, изменение набора предметных операций при сохранении согласованной диагностики и воспроизводимого execution plan. Наличие красивого интерфейса управления правилами подтвердит пользу интерфейса; отдельно нужно установить, требуется ли для него UT.

Ограничения выбора клиента конкретны: текущие public projects используют `net10.0`; [release state](../../../eng/documentation-release-state.json) различает source candidate `0.1.0-alpha.7` и recorded published baseline `0.1.0-alpha.1`. Это checked-in состояние, не свежая проверка NuGet feed. Для пилота закрепить реально доставляемую версию и проверить clean consumer. In-process restrictions не заменяют isolation и resource limits для недоверенных программ; это влияет на объём продукта, если такой ввод нужен клиенту. См. [SECURITY](../../../docs/SECURITY.md).

### 5.2. Более исследовательская гипотеза: проверка расширяемых compiler/runtime systems

Пользователь — maintainer компилятора, evaluator или plugin runtime; предполагаемый покупатель — владелец качества релизов соответствующей команды. Полезный результат — воспроизводимый дефект взаимодействия компонентов с маленьким counterexample, который экономит расследование и предотвращает регрессию.

PlanFuzz уже предоставляет значительную часть harness, но `Core`/`CLI` имеют `IsPackable=false`; CLI явно собирает Acme/Wist adapters, а один oracle привязан к UT lock schema. Значит, текущую исследовательскую инфраструктуру нельзя рекламировать как готовый инструмент для любого компилятора. Источники: [status](../../proposals/planfuzz/implementation-status.md), [CLI](../../../UniversalToolchain/UniversalToolchain.PlanFuzz.Cli/PlanFuzzCommandHost.cs), [lock oracle](../../../UniversalToolchain/UniversalToolchain.PlanFuzz.Core/CanonicalLockConsistencyOracle.cs).

Условие внешнего пилота: подключить уже существующую систему без её миграции на UT, сделать явный composition seam и включить применимые oracles. Сравнить с FsCheck/обычной тестовой обвязкой при том же бюджете. Считать adapter effort, triage time, replay reliability и подтверждённые разные root causes. Строить общую коммерческую testing-платформу до этого результата преждевременно.

### 5.3. Самая дорогая гипотеза: вычислительный DSL

Пользователь — владелец предметных вычислений или языка; покупатель — тот, кто несёт измеримую стоимость compute, latency или поддержки оборудования. Интерес к «универсальности» без программы, данных и ограничений не определяет продукт.

Честный конкурент — прямое использование подходящего backend или узкая обвязка над ним. Потенциальная ценность UT: меньшая стоимость изменений DSL, проверенные доменные преобразования либо соблюдение специальных semantics при разных execution routes. Если прямой backend решает задачу проще, наличие собственного SSA не оправдывает новый compiler stack.

### 5.4. Как проверить экономику без выдуманного TAM

Предлагаемый первый бюджет исследования — пять разговоров о реальных последних изменениях/ошибках в одном сегменте и до двух сопоставимых пилотных задач. Это организационный предел обучения, не статистически репрезентативная выборка и не уже проведённые интервью. Главный сигнал — согласие дать конкретный материал, владельца и время на интеграцию; слова «интересная технология» слабее.

Вопросы для интервью:

1. Какую формулу, правило, расширение или вычисление меняли в последний раз? Кто и сколько работал?
2. Что оказалось трудно проверить, воспроизвести или выпустить? Есть ли обезличенный пример?
3. Чем пользуются сейчас и почему существующего инструмента недостаточно?
4. Кто интегрирует решение, кто принимает результат и кто оплачивает сопровождение?
5. Какие runtime, версии .NET, ограничения данных, latency и требования к isolation обязательны?
6. Какое измеримое улучшение оправдает переход и как его проверить на одном пилоте?

Пилот фиксирует одинаковую задачу для UTS и сильного substitute. Учесть установку, интеграцию, изменение требования, тесты, диагностику, rollout и поддержку. Повторные изменения важнее единственного короткого demo; исторический [DSL evolution study](https://github.com/Misha1302/UniversalToolchain/blob/01e0a85d9b9742b3654476ec360f98d5d4027819/internal-docs/research/dsl-evolution-study/RESULTS.md) уже показывает, что marginal LOC и total cost могут расходиться.

Возможная первая модель дохода — оплачиваемая интеграция и поддержка ограниченного применения. Повторяющиеся потребности могут позднее обосновать поддерживаемую поставку или сервис. Это не доказательство масштабируемости: каждый уникальный язык может превратить работу в заказную разработку. Цена должна сопоставляться с подтверждённой ценностью и полной стоимостью внедрения/поддержки; выручку, объём рынка и сроки окупаемости по имеющимся данным оценить нельзя. Корневая [лицензия Apache-2.0](../../../LICENSE) сама по себе не создаёт платное предложение.

## 6. Наука: уже есть основа, нужно усилить доказательство

### 6.1. Сначала использовать CGO27

В [CGO27](../../../CGO27/paper/README.md) уже находятся статья, claim ledger, reproducible artifacts и эксперименты. По checked-in [results](../../../CGO27/RESULTS_SUMMARY.md):

- boundary study охватывает 42 primary/challenge формы; P2/P3 совпали на этом корпусе;
- Wist source-to-result содержит 30 программ и 240 записей: пять targeted faults, 24 valid controls и отдельный pre-existing failure P07;
- TensorRules содержит 12 случаев и 48 наблюдений через public SDK; это model-authored второй пакет, не независимо разработанный язык;
- проведены восемь mechanism ablations с соответствующими controls.

Это исторические результаты указанных в ledger commits, прочитанные при текущем аудите; здесь эти кампании заново не запускались. Числа разных корпусов не складываются в число независимых real-world defects. TensorRules проверяет shape/type/policy и не является численным tensor backend.

На 100 control records boundary study P2 выполнил 120 verifier invocations, P3 — 140: сокращение суммарного числа на 14,3% относительно P3. Оно не измеряет полное время компиляции. [Performance protocol](../../../CGO27/PERFORMANCE_ENVIRONMENT.md) задаёт собственные критерии, включая 25% сокращения вызовов в nontrivial clean/mixed strata; существующий результат не обосновывает efficiency headline. Decision-grade timing и independent external corpus остаются blocked. Источники: [ablation report](../../../CGO27/ABLATION_REPORT.md), [review findings](../../../CGO27/REVIEW_FINDINGS.md), [claim ledger](../../../CGO27/CLAIM_EVIDENCE_LEDGER.md).

### 6.2. Уточнить novelty относительно близких работ

| Первичная работа | Релевантное пересечение | Следствие для UTS |
|---|---|---|
| [Ratte, ASPLOS 2025](https://www.doc.ic.ac.uk/~afd/papers/2025/ASPLOS-Ratte.pdf) | Композиционные dialect semantics, reference interpretation и modular semantic fuzzing | Общая формула «семантика расширений плюс fuzzing» слишком широка для novelty claim |
| [First-Class Verification Dialects for MLIR, PLDI 2025](https://users.cs.utah.edu/~regehr/papers/pldi25.pdf) | Семантика в verification dialects и переиспользуемые инструменты проверки, включая transformations/transfer functions | Нельзя строить отличие на отсутствии semantic verification в MLIR ecosystem |
| [Optimuzz, PLDI 2025](https://prosys.kaist.ac.kr/publications/pldi25.pdf) | Optimization-directed fuzzing вместе с translation validation | Нужно выделить пользу конфигурационных/lifecycle contracts и сравнивать её отдельно от генерации программ |
| [Practical Formal Verification for MLIR Programs, preprint v1, 2026](https://arxiv.org/abs/2605.01124v1) | Ограниченная equivalence verification при различиях schedule/storage | Текущее соседнее направление учитывать; preprint не объявлять универсальным решением или рецензированным результатом |

В просмотренном related-work разделе CGO27 первые три работы не обсуждаются: это конкретный backlog литературного сопоставления. Anonymous manuscript, frozen corpora и thresholds данным стратегическим обзором не меняются. Обновление статьи должно отдельно соблюдать её provenance/anonymity workflow.

### 6.3. Основная гипотеза: composition contracts и reverification

Предлагаемая узкая формулировка:

> На независимо подготовленных расширениях pipeline типизированные обязательства помогают обнаруживать нарушения зарегистрированных инвариантов на нужной границе, а выборочное выполнение проверок сохраняет требуемую полноту при полезной полной стоимости по сравнению с проверкой всех применимых инвариантов и с обычной ручной интеграцией.

Здесь отдельно проверяются корректность declarations, качество локализации, стоимость интеграции и runtime overhead проверок. Неудача одной части сужает claim; её не компенсирует успешный результат другой.

Нужны следующие действия:

1. Использовать имеющийся [external fault kit](../../../CGO27/external-fault-kit/README.md) для независимо подготовленного и замороженного до просмотра результатов корпуса. Повтор автором новых ошибок не становится blind external validation.
2. Выделить случаи корректных declarations и отдельную robustness-группу с пропущенной invalidation/ложным preservation. Эти группы отвечают на разные вопросы и имеют отдельные знаменатели.
3. Сравнить P2/P3 с аккуратным typed C# pipeline, использующим те же verifier через явные callbacks и обычные preservation/dependency rules. При claim о переносе на другой framework нужен его стандартный pass-manager baseline.
4. Выполнить существующий pinned-machine timing protocol, не подбирая новые thresholds после измерений. Считать полную компиляцию, память, scheduler overhead и распределение времени; verifier invocation count остаётся вспомогательной метрикой.
5. Проверять стоимость написания и сопровождения contracts. Если declarative route требует больше интеграционной работы без выигрыша, это тоже результат.

LLVM уже реализует analysis invalidation и сохранение результатов; такой baseline нужен для сравнения добавочной ценности UT. Semantic invariant checking также не тождественен equivalence proof: замена сложения вычитанием способна сохранить типы и shape. Если соответствующего oracle нет, P3 тоже может её пропустить.

**Правило будущего независимого опыта.** Существующий [frozen protocol v3](../../../UniversalToolchain/Experiments/UniversalToolchain.ContractExperiments/STUDY_PROTOCOL_V3.md) сохраняется: несовпадение P2/P3 на заранее определённом корпусе нарушает критерий успешного воспроизведения. Для нового blind corpus до запуска нужен отдельный протокол. Устойчивое расхождение при корректном исполнении сохраняется как результат проверки гипотезы и исследуется независимым oracle; подтверждённый пропуск P2 учитывается как отрицательный результат. Такие случаи не исключаются как infrastructure failure и не добавляются в исторические знаменатели. Само по себе решение P3 не объявляется абсолютной истиной.

Восемь ablations показывают роль отдельных механизмов на подготовленных случаях. Они не оценивают распространённость ошибок в чужих системах. Результаты на корректных declarations обосновывают selective mode только в явно заданной модели доверия и полноты контрактов. Подтверждённый пропуск P2 внутри заявленного поддерживаемого режима блокирует claim о необходимой полноте до исправления или явного сужения этого режима. Ошибки declarations в robustness-группе определяют границы применимости и сохраняются в отчёте. Если полная стоимость не выигрывает по зафиксированным критериям, efficiency claim снимается; может остаться полезный результат по диагностике и composition checking.

### 6.4. Следующая гипотеза: PlanFuzz

Кандидат на вклад — проверка отношений между program, configuration и lifecycle: исключённый owner не активируется, независимое расширение не меняет наблюдаемое поведение, выбранный fallback соблюдает контракт, ресурсы живут достаточно долго.

При этом [ConfigFuzz](https://slaterlatiao.github.io/docs/configfuzz.pdf) уже исследует совместную генерацию configurations и обычного input, а [SynthFuzz](https://arxiv.org/abs/2404.16947) — custom mutations и покрытие сочетаний MLIR dialects. Новое утверждение должно выделять конкретные contract oracles и lifecycle dimension, а не только наличие нескольких изменяемых входов.

Нужно сравнить program-only, configuration generation, pairwise configurations и proposed schedule generation при одинаковых ресурсах. Совместный configuration/input baseline должен включать ConfigFuzz либо сопоставимую реализацию его принципа, если сам инструмент несовместим с target; отличия фиксируются явно. Отдельный контроль использует те же generators и oracles, чтобы не приписать search strategy эффект более сильной проверки. Предпосылка независимости расширений должна быть частью тестового контракта и внешней проверки, а не только декларацией проверяемой системы.

Lifecycle/schedule generation, соответствующий reduction, внешний adapter и equal-budget study ещё требуют работы по [implementation status](../../proposals/planfuzz/implementation-status.md). Считать разные подтверждённые root causes, time-to-confirmation, false positives/inconclusive, replay success и размер минимального случая. Seeded faults проверяют пригодность harness; старые известные issue не становятся новыми discovery results. Если выигрыш исчезает при одинаковых oracles или существует только на внедрённых faults, инструмент остаётся QA-помощником без заявленного превосходства исследовательского метода.

### 6.5. Третья гипотеза: стоимость независимой эволюции DSL

Имеет смысл только при внешних consumers и реальных change requests. Заморозить consumer, попросить независимо сформулировать расширение и учитывать adapters, tests, docs, migrations и общий elapsed effort. Различать уточнение уже известного query и совершенно новое semantic relation. Новый provider через заранее известный hook не доказывает способность автоматически понять любую новую семантику.

Такое исследование может показать точку амортизации общей инфраструктуры или полезный отрицательный результат. Ещё один toy example с LOC не закрывает вопрос внешней экономии. До появления материала оно не блокирует основной CGO27 результат.

## 7. Что это означает для семантического ядра и архитектуры

Нужна явная семантика выбранного домена: типы, значения, effects, ошибки, допустимые преобразования и критерий эквивалентности. Для численного домена добавляются shapes/layouts, aliasing, ownership, FP/reduction policy и условия target execution. Эти контракты могут жить в domain packages и обычных typed interfaces.

Общий FactStore/inference engine получает основание, когда независимые consumers повторно используют одни и те же знания и direct interfaces создают измеренную дублирующую стоимость. До этого selective invalidation увеличивает ответственность за корректность, не гарантируя полезного выигрыша. Доверенный descriptor, provenance и schema validation не удостоверяют истинность ложного математического закона.

Сохранить действующие границы: `LanguageCompiler` выбирает composition, `LanguagePlan` фиксирует её, runtime исполняет выбранный маршрут. План оптимизации конкретной программы действует внутри этого мира; он не является `LanguagePlan` и не разрешает скрытую повторную активацию backend. Численный IR может использовать существующие typed artifacts без обязательного раннего lowering в stack AIR. Общий framework не получает branches по Wist, tensor operation или названию GPU.

Текущий смысл universality — независимость framework от конкретного домена и возможность добавлять реализации. Он совместим с узким первым продуктом. Количество одновременно поддерживаемых языков и устройств само по себе не является критерием качества архитектуры.

## 8. Ближайший backlog и условия завершения

Это порядок решений и работы, не обязательство по календарным срокам. Оценки реализации появляются после выбора владельца задачи, доступного оборудования и исполнителей.

| Приоритет | Работа | Проверяемый результат | Что меняет решение |
|---|---|---|---|
| P0 | Согласовать научный headline с текущим CGO27 evidence и новым prior art | Claim-to-evidence matrix, явные границы и related-work delta | Если отличие исчезает, изменить research question до расширения реализации |
| P0 | Выбрать один внешний сегмент и одну проблему | Карточка реального случая, owner, substitute, критерий полезности | Без такого случая численный/product roadmap остаётся exploratory |
| P1, наука | Новый blind-corpus protocol поверх существующего kit | Заранее определённые группы, oracle, допустимые исключения, раздельные denominators | Результаты с incomplete declarations определяют условия применения и границы доверия selective mode |
| P1, наука | Сильный baseline и pinned-machine experiment | Сопоставимые verifier, полная стоимость, воспроизводимый receipt | При отсутствии выигрыша снять efficiency claim, сохранить честный результат |
| P1, пилот | Один внешний consumer: Wist либо PlanFuzz | Интеграция и одно реальное изменение, сравнение с substitute | Победа workflow без пользы UT не подтверждает framework differentiation |
| P1, для приёмки пилота | Устранить конкретные integration/release blockers выбранного consumer | Clean consumption закреплённого пакета, diagnostics, release receipt | API расширять только под обнаруженное ограничение |
| Условно | Numerical R1/R2 и первая итерация S1–S4 | Реальное CPU/GPU execution, oracle, matched backend baseline | Продолжить только при подтверждённой задаче и технической выполнимости |
| Позже | Общий semantic service, новые accelerators, автоматический partitioning | Отдельный measured case и acceptance criteria | Не включать автоматически в ближайшее ТЗ |

Первую научную и одну практическую линию можно вести параллельно, если хватает людей; это не три самостоятельных продукта. При одном исполнителе сначала завершать наименьший различающий эксперимент, затем пересматривать очередь.

### Критерии поворота или остановки

- **Нужны обычные expressions, substitutes достаточно:** ограничить Wist ролью reference/library или выбирать требуемую бизнес-функцию без предположения о необходимости нового compiler framework.
- **Находятся внешние composition defects и полезен reduction:** усиливать PlanFuzz/contract tooling и исследовательское позиционирование.
- **Есть тяжёлое доменное вычисление и собственные semantics:** открыть numerical track поверх готового backend с понятной целевой метрикой.
- **Selective checking не даёт полной экономии:** оставить conservative verification и сузить научное утверждение до обнаружения/локализации нарушений.
- **Для нескольких независимых consumers повторяется стоимость знания:** рассмотреть общий semantic service с direct-interface control.
- **Нет внешней потребности и независимого исследовательского эффекта:** поддерживать компактный исследовательский framework, сократить feature expansion. Уже вложенное время не является критерием следующей инвестиции.

## 9. Как из этого получить чёткое ТЗ

У каждого ближайшего требования должны быть: пользователь/исследовательский вопрос, вход и supported subset, наблюдаемый результат, сильная альтернатива, критерий приёмки, воспроизводимый материал и условие отказа. Открытые поля отмечаются явно; неизвестный процент ускорения не заменяется придуманным числом.

Для научной линии ТЗ может начинаться с отдельного blind-corpus protocol, integration baseline и существующего pinned-machine runner. Для Wist — с закреплённого clean-consumer пакета и одной предметной операции/версии формулы в выбранном host. Для PlanFuzz — с внешнего adapter/composition seam и воспроизводимого counterexample. Для аппаратной ветки уже подготовлены [R1/R2 и S1–S4](SPEC_RESEARCH_PLAN.md).

**Решение о направлении определяется результатом этих проверок.** Семантическое ядро, количество DSL и новые backend — средства достижения выбранной цели; ни одно из них не служит самостоятельным доказательством ценности проекта.
