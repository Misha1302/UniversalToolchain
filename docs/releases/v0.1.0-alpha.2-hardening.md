# Wist 0.1.0-alpha.2 hardening and migration

This release is a deliberate compatibility boundary reset. It closes runtime-policy bypasses and does **not** promise source or binary compatibility with `0.1.0-preview.1`, `0.1.0-alpha.1`, or runtime assemblies with assembly version `1.0.0.0`.

## Supported entry point

Application code should reference only `UniversalToolchain.Wist` and construct `WistEngine`. Runtime implementation assemblies remain package runtime assets but are not supported compile-time APIs.

- Replace `WistBackend` with `WistEngineOptions.BackendId` using exactly `cil` or `interpreter`.
- Replace `WistPreset` with `WistDialectSource` or `WistEngineOptions.FromPresetId(...)`.
- Replace `CompileFunc`/`WistFunc` wrappers with `Compile<TDelegate>` or `TryCompile<TDelegate>`.
- Replace `WistValidationResult.Message` parsing with structured `Diagnostics` and `Exception` handling.
- There is no facade-level compilation-cache compatibility switch. Cache immutable `WistProgram<TDelegate>` instances in host code only when ownership and invalidation are explicit.

Low-level Wist execution configuration, workflow, raw host, and the former runtime facade are internal. No compatibility shim is provided because restoring one would recreate the policy bypass fixed by this release.

## Backend and preset behavior

`WistEngine.Create` validates the selected backend against the resolved dialect before returning. `Evaluate`, `Validate`, `Compile`, and `TryCompile` all use the same selected backend. Each shipped preset declares its supported set and default backend; the exact catalog is checked against all packaged `.wistdialect` files.

## Runtime identity

Runtime implementation assemblies use assembly generation `2.0.0.0`. Loading is root-authoritative: implementation assemblies are owned by a collectible runtime context, while an exact configured contract dependency may be shared with the default context only when both path and full assembly identity match. An incompatible `1.0.0.0` checkout or a same-name assembly preloaded from another path is rejected or ignored before runtime activation rather than unified process-wide. This is an assembly-loading boundary, not a process-security sandbox.

Implementation-owned numeric values are normalized at the public Wist and Language SDK boundaries. Arithmetic based on `NumbersModule.Core.RealNumberImpl` is exposed as `System.Double`, so results from independent runtime contexts have stable public type identity.

## Complete compatibility ledger

`eng/wist-api-compatibility.csv` is the machine-checked migration map for every reviewed removed/changed facade symbol and former package compile asset. `Tools/check-wist-api-compatibility.py` rejects missing, duplicated, empty, or unclassified entries.
