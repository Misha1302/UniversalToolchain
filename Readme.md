## 2. Аннотация
Проект заключается в разработке в области проектирования языков программирования - архитектуры универсального тулчейна (от англ. Toolchain) - Universal Toolchain. Основная идея - преодоление принципиальных ограничений, присущих языкам программирования общего назначения. Ключевая проблема, решаемая в рамках проекта, заключается в неспособности любого **фиксированного** языка эффективно решать весь спектр задач из-за фундаментального компромисса между выразительностью, производительностью и специализацией. 

Одним из наиболее ярких примеров такой проблемы - отсутствие обобщенной арифметики в C# до версии 10 включительно. На текущий момент (октябрь, 2025 год) в новейшей версии Unity используется диалект C# 9.0. Разработка игр - это область, где кода с математическими расчетами может быть много. Его удобно писать на функциональных языках, например на Haskell или F#. Рассмотрим, как будет выглядеть код метода `SquareMagnitude` на C# в Unity.

```CSharp
double SquareMagnitude(double a, double b) => a * a + b * b;
float SquareMagnitude(float a, float b) => a * a + b * b;
long SquareMagnitude(long a, long b) => a * a + b * b;
int SquareMagnitude(int a, int b) => a * a + b * b;
// ... и так далее для byte, sbyte, ushort, uint, ulong, decimal, других потенциальных числовых типов данных
```

Как видно, идет большое дублирование кода. C# не лучшим образом подходит для написания математического кода. Данная проблема являтся частным проявлением более общей фундаментальной ограниченности - невозможности эффективного расширения семантики языка без изменения его базовой реализации.  Существующие решения, такие как препроцессоры, системы макросов или внешние генераторы кода, оказываются недостаточными, поскольку они:
1. Все еще оперируют в рамках и ограничениях языка
2. Не имеют доступа к ключевым этапам компиляции (middle end, backend, промежуточные звенья)
3. Усложняют отладку
4. Не гарантируют семантическую и синтаксическую согласованность

Предлагаемое проектное решение основано на парадигме **расширяемого программирования** (Extensible programming), возведенной в абсолют через реализацию модульной архитектуры. Каждый компонент языка, от лексера и парсера до системы типов и генератора бинарного кода, представлет собой независимый и композируемый набор модулей. Ключевыми инновациями архитектуры являются:

#### Микросервисная организация тулчейна
Множества модулей реализованы как независимые веб-сервисы, взаимодействующие через стандартизированные API. Таким образом обеспечиается:
* Физическое разделение компонентов языка
* Независимость технологических стеков реализации множеств модулей
* Возможность распределенной оптимизации и специализации

#### Абстрактный байткод на основе шитого кода (threaded code)
Универсальное промежуточное представление в форме `(tags, pre-ops, main-ops, post-ops)` позволяет встраивать свою логику на уровне инструкций без взаимных зависимостей. Это позволяет сократить количество связей между плагинами с `O(n^2)` до `O(n)`. Например модуль для проверки типов может добавлять проверки в `pre-ops`, модуль арифметики - в `main-ops`, а модуль логирования - в `post-ops`. При этом каждый модуль ничего не будет знать о других модулях - все они будут независимы. 

#### Адаптивная система оптимизаций
Абстракция - враг оптимизаций. Но я считаю, что способ сделать многие оптимизации zero-cost. Используя агрессивный инлайнинг двух уровней, peephole и pattern-matching оптимизации, есть возможность добиться хорошего упрощения промежуточных и конечных представлений кода. Рассмотрим преобразование абстрактной операции установки значения в переменную:

```CSharp
// Исходный код
x = 2

// Сгенерированный байткод
([LoadRef], [LoadReferenceX], [], [])
([LoadReadonlyRef], [PushInt2], [], [])
([Set], [SetLocal], [], [])

// После инлайнинга
var a = new VariableWrapper<int>(0);
var b = 2;
a.Set(b);

// После оптимизации pattern-matching
VariableWrapper<int>._variables[0] = 2;

// Финальный ассемблерный код
mov rcx, 2
```

Проектное решение **не является** еще одним языком программирования. Это - мета-система для конструирования языков общего и специализированного назначения (general-purpose-language, domain-specific-language). Практическая значимость проекта заключается в создании методологий методологической и технологической основы для поколения инструментов программирования, которые:
1. Совмещают выразительность и производительность
2. Позволяют инкрементально адаптировать язык к меняющимся требованиям
3. Снижают порог входа в предметно-ориентированные области за счет кастомизации языка

Архитектура была верифицирована на примере реализации toolchain'а языка Wist, где различные аспекты системы (модульная организация, трансформация байткода) продемонстрироваи свою практическую применимость и эффективность. В рамках этого эксперимента удалось показать, что даже для минималистичного языка можно создать адаптивные оптимизации и специализированные расширения, улучшающие как выразительность, так и производительность.

UniversalToolchain представляет собой не просто техническое решение, а концепцию в проектировании языков программирования, переводящих их из категории **фиксированных** инструментов в **адаптивные** системы, способных эволюционировать в ритме с задачами бизнеса или науки. 


## 3. Обоснование актуальности
Я называю трилеммой проектирования языков программирования невозможность для одного, статически определенного языка одновременно обладать тремя ключевыми свойствами в их максимальном выражении:
1. **Выразительность и абстракции**: Язык должен снижать когнитивную нагрузку на программиста, интуитивно и лаконично описывать сложные концепции, минимизируя boilerplate-код
2. **Производительность времени выполнения**: При возникновении потребности, компилятор должен быть способен за разумную асимптотическую сложность генерировать высокопроизводительный исполняемый код (в первую очередь, точки зрения использования памяти и времени выполнения).
3. **Специализация и адаптивность**: При возникновении потребности, язык должен иметь возможность расширяться, например, через написание плагинов, чтобы обеспечить оптимальное решение задач конкретных предметных областей (Domain-Specific Areas), предлагая идиомы, конструкции, семантику, которые были бы полезны в данной области

Любой фиксированный язык вынужден находить баланс в данной трилеме. Например, Python, JavaScript или Ruby жертвуют производительностью времени выполнения, в пользу выразительности и динамичности. C++ и Rust предлагают высокую производительность и относительно хорошие абстракции, но за счет сложности языка и высокого порога входа. Языки вроде C и C-- обеспечивают предсказуемую высокую производительность, но почти лишены возможности реализации абстракций высокого уровня.

### Конкретные проявления проблемы
#### 3.1. Проблема семантического разрыва (Semantic Gap)
Между концепциями предметной области и примитивами, механизмами, предоставляемыми языком, существует разрыв. Программист должен вручную переводить высокоуровневые концепции на уровень конструкций языка. Этот процесс не только трудоемок, но также повышает технический долг, усложняет поддержку кода, повышает шанс возникновения ошибок.
* **Пример из аннотации: Отсутствие обобщенной арифетики в C# 9.0.**  Задача - написать функцию (метод), вычисляющую квадрат длины двумерного вектора для любого числового типа. В идеальном мире мы имеем что-то подобное: `T SquareMagnitude<T>(T a, T b) where T : Number => a * a + b * b; `. Или, как можно написать в F#: `let inline squareMagnitude x y = x * x + y * y`. Однако, в используемой версии языка, такая возможность отсутствует. Разработчик сталкивается с выбором:
  * Дублирование кода: Создание множества почти одинаковых методов для `int`, `long`, `float`, `double`, `decimal`, ... - нарушает принцип DRY, увеличивает объем кода, повышает когнитивную нагрузку, увеличивает технический долг.
  * Использование динамической типизации: Использование `dynamic` значительно замедляет код, что недопустимо в hot функциях, а также накладывает дополнительные ограничения на компиляцию (например, невозможность использования AOT компиляции)
  * Использование обобщений с ограничениями где это возможно: Например, для коллекций это работает, но для арифметических операций — нет. Это вынуждает писать обертки или использовать рефлексию, что также неэффективно и небезопасно.

**Вывод**: язык не позволяет элегантно выразить простую математическую абстракцию, заставляет разработчиков увеличивать тех. долг.

#### 3.2. Проблема статичности языковой экосистемы
Эволюция классического языка программирования - часто медленный и бюрократический процесс. Новые функции, библиотеки, парадигмы должны пройти долгий путь утверждения комитетами по стандартизции, а после реализованы в основных компиляторах-гигантах (GCC, Clang, Roslyn и т.д.) и только затем стать доступными разработчикам. Наука развивается с гораздо большей скоростью, чем ее идеи внедряются в меинстрим. 

* **Пример: Асинхронное программирование.** Появление многоядерных процессоров и распределенных систем сделало асинхронность и параллелизм критически важными. Языки вроде JavaScript и C# отреагировали на это введением ключевых слов `async`/`await` на уровне языка. Однако это потребовало фундаментальных изменений в компиляторах и runtime-средах. Языки, которые не были спроектированы для этого с самого начала (например, C++), долгое время предлагали лишь библиотечные решения (`futures`, `promises`), которые были менее удобны и выразительны. В рамках UniversalToolchain подобная функциональность могла бы быть добавлена как множество независимых модулей, без необходимости переписывания компилятора и других частей языка. 

#### 3.3. Проблема Domain-Specific Languages (DSL)
Попытки создать предметно-ориентированный язык для решения специфических задач (например написание шейдеров, конфигураций, парсеров), упираются в две основные проблемы:
1. Создание языка с нуля: Для более-менее сложных DSL'ей требуется разработка всего тулчейна: лексера, парсера, компилятора, отладчика, системы типов, промежуточных представлений, оптимизаторов и т.д. Это огромные трудозатраты, неподъемные для большинства проектов.
2. Использование метапрограммирования хост-языка: Создание внутренного DSL на базе существующего языка (например, Ruby, Scala, Racket, Lisp) понижает порог входа, но при этом имеет ограничения и особенности хост-языка. Часто это негативно сказывается на производительности и синтаксических и семантических правилах.

#### 3.4. Недостаточность существующих решений для расширяемости
Как написано в аннотации, существующие механизмы расширения **семантики** оказываются не идеальными:
1. Препроцессоры (clang/gcc): Работают на уровне текста, не беря во внимание семантику. Это приводит к проблемам, вида: `#define max(a, b) ((a) > (b) ? (a) : (b))`. А также усложняет отладку.
2. Системы макросов (Lisp, Rust): Продвинутые и полезные механизмы, но работают все еще на уровне AST. Они ограничены рамками расширяемости дерева. Макросы в Rust не имеют доступа к информации о типах после этапа вывода типов и не могут участвовать в генерации конечного машинного кода.
3. Внешние генераторы кода (например, кодогенерация на основе атрибутов в Roslyn): имею почти все те же ограничения, что и системы макросов. Но способны генерировать более низкоуровневые части, например байткод. Все еще неспособны учавствовать в генерации машинного кода или добавлять новые механизмы в языки (например, монады или template'ы в языки, такие как C#).

Лично мне хотелось бы иметь возможность писать на C# высокоэффективный код. Сам язык предоставляет много возможностей для данной цели, но не хватает авто-векторизации, качественной аллокации регистров, loop-unrolling, fastcall convention и других оптимизаций (даже в PGO). Качество при AOT компиляции неплохое, но все равно уступает C/C++, даже если писать листинг правильно через unsafe-код.

**Заключение по актуальности**
Современная индустрия языков программирования не поспевает за краем науки и, иногда, за требованиями бизнеса. Потребности в высокой производительности (игры, научные вычисления, HFT, шейдеры) требуют от языков программирования гибкости и адаптивности, которые не могут обеспечивать классические фиксированные языки. Например, в HFT было бы не плохо подключить в C различные NP-hard/complete-solver'ы для около-идеальной аллокации регистров или простеньких супероптимизаторов для маленьких функций. 

Проект UniversalToolchain предлагает отказ от монолитной архитектуры и переход на множество независимых модулей, которые помогли бы преодолеть трилему и добиться одновременной выразительности, производительности и заточенности под задачу. 

## 4. Цель и задачи
**Цель проекта** - разработка основы для создания адаптивного и композируемого toolchain'а, который позволит преодолеть ограничения фиксированных языков за счет реализации парадигмы расширяемого программирования в модульной и микросервисной архитектуре. 

Для достижения цели необходимо решить следующие задачи:
#### Задача 1. Разработка модульной, микросервисной архитектуры тулчейна с четкой стандартизацией интерфейсов между компонентами.

#### 4.1.1. Декомпозиция традиционного компилятора на независимые компоненты
Каждый "традиционный" компилятор (например GCC) представляет собой приложение на (относительно) монолитной архитектуре. Проект предлагает физически разделить некоторые этапы на независимые сервисы, взаимодействующие через API (например, REST с сериализацией DTO в JSON).
  * **Пример архитектуры**:
    * **Сервис лексера и парсера**: Принимают на вход исходный код, возвращают абстрактной синтаксические дерево
    * **Сервис синтаксичского анализа**: Принимает AST, возвращает аннотирование AST. Например, добавляет информацию о времени жизни сущностей, разрешает типы и т.п.
    * **Сервис транслятора в IR**: Принимает аннотированное AST и преобразует его в универсальное промежуточное представление (universal IR).
    * **Сервис высокоуровневых оптимизаций**: Принимает IR и применяет к нему цепочку оптимизирующих модулей, возвращает оптимизированный IR. Оптимизации выполняются общие для всего IR, без зависимости от целевой архитектуры
    * **Сервис генерации кода**: Принимает оптимизированный IR и генерирует исполняемый код под целевую платформу (можно использовать, например, LLVM)
  * Преимущество: Каждый сервис может быть реализован на своем наиболее подходящем технологическом стеке. Например парсер на ANTLR и C#, оптимизатор на C++ и т.п.
#### 4.1.2. Стандартизация форматов данных и протоколов обмена
Для обеспечения совместимости между сервисами необходимо определить универсальные форматы представления ключевых структур данных:
  * **Спецификация для AST**: Универсальный формат описания узлов дерева должен позволять описывать синтаксические конструкции любых языков может выглядеть так: 
    ``` 
    {
      "NodeType": "BinaryExpression",
      "Lexeme": {
        "Text": "+",
        "Line": 123,
        "CharIndex": 23
      },
      "Children": [ /* other nodes */ ]
    }
    ```
    Для удобства описания различных инструкций также можно добавить такой тип ноды, как Scope - он позволит быть как-будто контейнером для инструкций и позволит контролировать уровень вложенности.
  * **Специикация для IR**: Детализация этой спеицификации является ключевой задачей и будет рассмотрена отдельно.
#### Задача 2. Проектирование универсалього и расширяемого промежуточного представления 
Такие промежуточные представления как IR или MLIR, исправили множество существующих проблем и упростили генерацию кода. Но когда нам нужно добавить новую функциональность (например, проверку границ, логирование, специальные оптимизации), мы сталкиваемся с необходимостью:
1. Модифицировать существующие проходы компилятора
2. Нарушать инкапсуляцию между компонентами
3. Создавать сложные взаимосвязи между системами

Концепция шитого кода (threaded code), исторически использовавшаяся в интерпретаторах и Форт-системах, предлагает иной подход, который хорошо соответствует требованиям расширяемости.

#### Преимущества подхода
#### 4.2.1. Решение проблемы взрыва зависимостей между модулями
В традиционной архитектуре компилятора с N модулями количество потенциальных взаимодействий между ними примерно O(N^2). Каждый модуль должен знать о существовании других модулей и корректно с ними взаимодействовать
* **Пример проблемы**: Модуль проверки границ памяти и модуль логирования операций. Модули должны быть скоординированы, надо решить, какой из них выполняется первым, не конфликтуют ли.
* **Решение через шитый код**: Каждый модуль добавляет свои операции в соответствующие "слоты" `pre-ops`, `main-ops`, или `post-ops`, не зная о существовании других модулей (если не требуется). Система гарантирует поседовательное выполнение всех операций. Например:
  ```CSharp
  // Исходная операция инкремента указателя
  ([Ptr], [], [IncrementPointer], [])

  // После подключения модуля проверки границ
  ([Ptr], [CheckBoundsUpper], [IncrementPointer], [])

  // После дополнительного подключения модуля логирования
  ([Ptr], [CheckBoundsUpper, LogPointerPre], [IncrementPointer], [LogPointerPost])
  ``` 
  Модуль проверки границ и модуль логирования были подключены независимо и без какой-либо координации между ними. Количество связей остается O(N) - модуль-ядро. 

#### 4.2.2. Сохранение семантической информации на всех этапах компиляции
  Традиционные IR часто теряют высокоуровневую семантику в процессе трансформаций. Шитый код же сохраняет структуру `(tags, pre-ops, main-ops, post-ops)`, позволяя модулям работать с семантически более богатыми конструкциями.
  * **Конкретный пример**: Рассмотрим операцию доступа к элементу массива
    ```CSharp
    // Исходный код
    matrix[row, col] = 42

    // Традиционное низкоуровневое представление (псевдокод SSA):
    temp1 = row * matrix.stride_row
    temp2 = col * matrix.stride_col  
    address = matrix.base + temp1 + temp2
    store(address, 42)

    // Наше промежуточное представление:
    ([Set, MatrixInt32], 
    [CheckMatrixBounds(row, col), AcquireMatrixLock], 
    [SetMatrixElement(row, col, 42)], 
    [ReleaseMatrixLock, LogMatrixWrite])
    ```
    Представление сохраняет семантику установки элемента матрицы, позволяя специализированным модулям применять матрично-специфичные оптимизации, которые были бы невозможны при работе с низкоуровневыми операциями.

#### 4.2.3. Естественная поддержка cross-cutting функциональности
  Многие аспекты программирования, такие как логирование, профилирование, являются сквозными - они затрагивают множество различных операций в программе. Шитый код предоставляет естественный механизм для их реализации.
  * **Паттерн "Декоратор" на уровне байткода**: Каждый слот действует как точка для подключения функциональности к основной операции. Например:
    ```CSharp
    // Чтение из файла
    ([FileHandle], 
    [ValidateHandle, AcquireFileLock, LogReadStart], 
    [ReadData], 
    [ReleaseFileLock, LogReadComplete, UpdateMetrics])

    // Сетевой запрос
    ([NetworkConnection],
    [ValidateConnection, StartTimeoutTimer],
    [SendRequest],
    [StopTimeoutTimer, UpdateNetworkStats])
    ```

#### 4.2.4. Динамическая адаптивность и специализция
Посколько структура шитого кода уницифирована, система может динамически перестраивать последовательности операций на основе статически известной информации или профилировочных данныхю
* **Пример специализации**: Если возможно доказать, что чтение данных будет производится всегда в допустимых границах, то ситема может удалить операцию `CheckBounds` из `pre-ops` и, тем самым, ускорить код. Если профилировщик показывает, что логирование слишком затратно, то логирование может быть временно отключено для соответствующей операции.

#### Реализация IR
* Создание представления в формате `(tags, pre-ops, main-ops, post-ops)`
* Реализация сериализации IR в JSON-строку
* Реализация виртуальной машины для интерпретации шитого кода (для отладки и базовой реализации)
* Создание базовых модулей для фундаментальных операций (арифметика, операции потока управления и т.п.)

#### Задача 3. Реализовать базовые интерфейсы и их имплементации 
Важно, чтобы типов инструкций было минимальное количество, желательно, чтобы они были еще и абстрактными. Для этого допустим, чтобы инструкции работали не на уровне типов, а на уровне контрактов. Например, если в выдуманном языке мы имеем:
```CSharp
a = 2
--------------------
LoadI32 2
SetLocal a
```
То в нашем случае это будет:
```CSharp
a = 2
--------------------
LoadReadonlyRef a
LoadRef 2
Set
```

Перечисленные выше инструкции могут иметь следующее определение (на C#):
```CSharp

public interface IGettable<out TSelf> where TSelf : IGettable<TSelf> {
    public TSelf Get();
}

public interface ISettable<out TSelf> where TSelf : ISettable<TSelf> {
    public TSelf Set();
}

public interface IReference<TSelf> : IGettable<TSelf>, ISettable<TSelf>
    where TSelf : IGettable<TSelf>, ISettable<TSelf>;

void LoadReadonlyRef_a(out IGettable<int> result) =>
  result = (IGettable)VariableWrapper<int>.GetRef(0);

void LoadRef_2(out IReference<int> result) =>
  result = Constants.GetRef(0);
```

Как видно, происходит оперирование абтрактными типами, которые, в последствии, могут быть упрощены до конкретных. Почему бы не использовать сразу примитивы? Потому что, в таком случае, связность между плагинами резко возрастает чуть ли не до N^2. Условному плагину для арифметики придется учитывать не только int, long, float, double, decimal и другие типы, но также те, что были реализованы в других модулях. Например, если были реализованы комплексные числа, то придется их поддерживать еще и в плагине арифметики, сравнения, алгебраическом упрощении выражений, перевода значений в строки и т.д. А если потом мы реализуем сюрреальные, дуальные, пи-адические числа... Либо мы перестанем поддерживать модули, либо получим огромный технический долг. Но вместо того, чтобы работать с типами в лоб, введем, например для арифметики, свои интерфейсы:
```CSharp
public interface IBinaryOperation<TSelf> where TSelf : IBinaryOperation<TSelf>
{
    public static virtual bool IsCommutative() => false;
    public static virtual bool IsAssociative() => false;

    public static virtual bool IsDistributive<TOther>() where TOther : IBinaryOperation<TOther> => false;

    // others if you need
}

// Пример интерфейса IMulable, предоставляющий оператор умножения
public interface IMulable<TSelf> : IBinaryOperation<TSelf> where TSelf : IMulable<TSelf>
{
    public static abstract TSelf Mul(TSelf a, TSelf b);


    static bool IBinaryOperation<TSelf>.IsCommutative() => true;
    static bool IBinaryOperation<TSelf>.IsAssociative() => true;

    static bool IBinaryOperation<TSelf>.IsDistributive<TOther>() =>
        typeof(TOther).IsAssignableFrom(typeof(IAddable<>).MakeGenericType(typeof(TSelf)));
}
```

Да, они слегка увеличат когнитивную нагрузку, но несущественно. Все мы знакомы с бинарными операциями и, в частности, умножением. Теперь можно спокойно писать абстрактный код для арифметики и не беспокоиться, что код придется изменять при добавлении новых типов чисел - Open-Closed принцип соблюден. 

#### Задача 4. Создание механизма подключения и управления модулями
#### 4.4.1. Разработка системы регистрации и обнаружения модулей.
Модули должны подключаться к тулчейну. Для этого необходимо реализовать систему, которая позволит подключать нужны модули, например, используя конфигурационный файл. Конфигурация будет содержать ссылки (uri - путь к файловой системе, веб-ссылку на библиотеку или другое) на загрузку модулей. Что важно, зависимости образуют собой Directed-Acyclic-Graph (DAG), поэтому не нужно импортировать уже импортированные модули, но при этом проверять, чтобы циклы не существовали. При этом загружать модули можно, используя "продвинутый" DFS с цветами (для гарантии отсутствия циклов). Так как граф ацикличный и направленный, то DFS гарантированно импортирует ответвление, а значит, со временем, и весь граф.

Взаимодействие между плагинами хорошо реализуется через события. При необходимости, можно реализовать паттерн EventBus. 

#### Задача 5. Верификация архитектуры путем реализации эталонного тулчейна для языка Wist
#### 4.5.1. Разработка фронтенда
Предстоит задача - разработать универсальный лексер и парсер, с возможностью расширения синтаксиса и семантики за счет написания модулей.
#### 4.5.2. Разработка middle end'а
Предстоит реализовать абстрактное синтаксическое дерево, а также API для его модификации. Также стоит сделать упор на расширяемость дерева через модули. Помимо AST, также необходимо реализовать байткод и API для операций над ним.
#### 4.5.3. Разработка простейшего бекенда и API для его замены
На **первом этапе** нет смысла думать о высоко-эффективном бекенде языка. Для начала, стоит реализовать простой интерпретатор шитого кода. Качественная абстракция над исполнителем требуется для **бесшовной замены** одного бекенда на другой. Например, можно будет заменить интерпретатор на компилятор, основанный на LLVM. Это позволит сильно уменьшить время исполнения программ, уменьшит потребление памяти и, возможно, уменьшит количество зависимостей исполнямого файла. Возможно, для конкретного языка потребуется формализация работы его абстрактной виртуальной машины (AVM) (как для C++), чтобы **исключить существование Undefined Behaviour**. Это важно, так как UB - это огромная проблема в существующих языках (никакие плюсы, по типу возможностей для оптимизаций, не смогут его оправдать). При создании исполнителя, стоит убедиться, что его поведение полностью соответствует формальному описанию абстрактной исполняемой машины. 

Некую часть исходного кода (для задач 4.5.1, 4.5.2 и 4.5.3) можно взять из предыдущих проектов, чтобы процесс разработки шел быстрее. К счастью, код соблюдает принципы SOLID и его легко переиспользовать.

**Задача 5** является самой важной, ведь исходный код полученного решения будет использоваться другими разработчиками (ага, если бы они существовали. TODO: УДАЛИТЬ), чтобы реализовывать собственные языки программирования и иные утилиты.

## 5. Анализ существующих решений
Анализ современных подходов к расширению и созданию языков выявляет проблемы, которые желательно решить в реализуемом проекте. В также должна помочь модульная микросервисная архитектура и промежуточный шитый код.

#### 5.1. Макросы и метапрограммирование
#### 5.1.1. Текстовые макросы (препроцессор GCC/clang)
* **Ограничение**: Работа на уровне лексем без понимания синтаксиса и семантики.
* **Пример проблемы**: `#define MAX(a, b) ((a) > (b) ? (a) : (b))` и использование `MAX(++x, ++y)`
* **Потенциальное решение**: Предоставление механизмов для написния кода без использования макросов. Можно предоставить возможность писать функции, которые будут инлайнится на этапе генерации AST. Также помогут гигиеничные макросы и написание модулей для реализации решений еще более специализированных задач.

#### 5.1.2. Гигиеничные макросы (как в Sheme или Racket) и процедурные макросы (как в Rust)
* **Ограничение**: Выполняются на этапе AST и не имеют информации, о семантике (например, о типах), не имеют возможности влиять на более низкоуровневые этапы.
* **Пример**: Макрос для векторных операций в Rust не может оптимизировать примитивные алгебраические тождества, так как эта информация доступна только на более поздних этапах компиляции.
* **Потенциальное решение**: Семантика сохраняется в форме байткода на всех этапах (кроме фронтенда и AST). Модули имеют доступ к каждому этапу компиляции и имеют возможности оптимизировать сгенерированный код и реализовывать различные трансформации.

#### 5.2. Внешние генераторы
* **Ограничение**: Очень мощные механизмы, в отличии от гигиенических макросов. Но все еще работают на основных этапах компиляции, не имея возможности повлиять на генерируемый низкоуровневый код. Но в таких языках, как C#, могут генерировать и модицифировать даже байткод (но только в стандартных реализациях. В Unity не везде возможно).
* **Пример**: Lombok в Java/C# генерирует боерплейты, но не может оптимизировать вызовы (инлайнить, мемоизировать результат и т.п.)
* **Потенциальное решение**: Генератор кода может сделать "пометку" в tags инструкций байткода. Затем модуль, написанный для бекенда, распознает метку и применит к коду специфичные оптимизации.

#### 5.3. Плагины для компиляторов (в частности LLVM)
* **Ограничение**: Невозможно сохранить высокоуровневую семантику инструкций. Плагины могут конфликтовать друг с другом или имеют повышенную связность между собой
* **Пример**: Плагин thread-safety и плагин для мемоизации могут некорректно взаимодействовать.
* **Потенциальное решение**: Используя структуру байткода, заставить плагин thread-safety выполнять блокирование раньше всех инструкций, а разблокирование после исполнения всех других.

#### 5.4. Платформы для создания языков
#### 5.4.1. JetBrains MPS
* **Преимущество**: Мощная система для создания языков с нетривиальным синтаксисом и поддержкой IDE
* **Ограничения**: Слишком примитивная система компиляции
* **Потенциальное решение**: Проект позволяет управлять кодом на любом этапе, сохраняя семантику всех уровней

#### 5.4.2. Xtext
* **Ограничение**: Жесткая привязка к Eclipse и JVM
* **Потенциальное решение**: Проект не привязан ни к одному языку программирования и IDE


**Вывод**: Хоть проект и имеет много преимуществ над существующими решениями, он имеет и недостатки. UniversalToolchain требует умения от программиста мыслить на высоких уровнях абстракций. Также проект требует строгого соблюдения SOLID и принципы DRY, KISS, YAGNI и другие. 

**Основные конкуретноспособные идеи**, предоставляемые проектом:
1. Tags как информация о всех уровнях семантики инструкции
2. Продуманная система абстракций, для снижения связи между плагинами
3. Возможность плагинизации любой части языка - удобное и простое API

## 6. Roadmap
Учитывая скромные временные рамки, ресурсы и ограниченность команды (автор и его кот), карта фокусируется на создании минимально-жизнеспособного продукта (MVP), демонстрирующего ключевые преимущества проекта.

#### 6.1. Реализация простого языка программирования
**Цель**: используя код языка Wist (или, хотя бы, идеи разработки) из предыдущего проекта, перестроить архитектуру и реализацию под ту, что требует UniversalToolchain. Удалить весь "лишний" код, появившийся в процессе изменения языка.

**Конкретные задачи**:
1. Реализация структуры байткода
2. Создание примитивного интерпретатора
3. Написание модулей для минимального языка
   * Модуль числовой арифметики
   * Модуль булевой арифметики
   * Модуль базовой интероперабельности с C# (начать с статических публичных методов)
   * Модуль условных переходов
   * Модуль локальных переменных
   * Модуль циклов (for, while)
   * Модуль функций (**важно**: зависят от локальных переменных)
   * Модуль списков

   * Модуль синтаксического сахара для unified calls
